## Checkpoint 17 — Phase 2: Donation → Campaign → Wallet chain traced end to end; government escalation was a dead end

Traced the full path a rupee takes: donor donates → AI fraud+risk scoring → NGO review (or government escalation for high-risk) → beneficiary assignment → wallet creation/top-up → campaign stats. Confirmed the AI integration layer is genuinely solid first (exact-field-match verified between `ai.service.js` and both `fraud_agent`/`risk_agent`'s real Pydantic schemas, not just the mocks) - then found and fixed real breaks further down the pipeline:

- **Most severe bug this session: the government escalation path was a dead end.** When a high-risk donation gets escalated and a government reviewer approves it, `government.service.js` set `donation.status = "APPROVED_BY_GOVT"` - a status the NGO's entire review pipeline (`getPendingDonations`, `assignDonationToBeneficiary`, `approveDonation`) never looked for. The donation vanished from every actionable queue permanently: no beneficiary could ever be assigned, no wallet ever created, the donor's money was simply stuck with no path forward. Fixed by including `APPROVED_BY_GOVT` in the NGO-actionable status set in all three places, so a government-cleared donation flows back to the NGO exactly like a normal one.
- **Data-integrity bug: campaign financial stats were double-counted.** `ngo.service.js approveDonation()` called `createWallet()` (which internally increments `Campaign.totalAllocated` and `totalWalletsCreated`) and then did its own *second*, redundant increment of the same fields right after. Every approved donation inflated the campaign's public transparency numbers by 2x. Removed the redundant increment; `createWallet()`/`creditWallet()` now own that update exclusively.
- **Logic bug: a beneficiary's second donation could never be approved.** `createWallet()` requires `beneficiary.status === "APPROVED"`, but approving a beneficiary's *first* donation flips their status to `"ACTIVE"` - so a second donor (or the NGO allocating a second donation to someone with ongoing need) would hit "beneficiary not approved" and be stuck, even though `creditWallet()` (a top-up function) already existed for exactly this case and was simply never called from this path. `approveDonation()` now checks for an existing active wallet first and routes to `creditWallet()` when one exists.
- **Missing workflow: donors received zero notifications for their entire donation lifecycle** - not on AI block, not on government escalation, not on NGO approval, not on NGO rejection. The `Notification` model already had a `DONATION_SUCCESS` type defined with no code anywhere that ever used it - a designed-but-never-wired notification. Added donor notifications at every real decision point (AI block/escalate, NGO approve/reject, government approve/reject), plus an NGO notification when a government-cleared donation needs their action. Added two new notification types (`DONATION_REJECTED`, `DONATION_ESCALATED`) to the model enum to cover cases the existing single type couldn't distinguish.
- Verified (not assumed): `createCampaign` already correctly blocks unapproved NGOs from creating campaigns (defensive check beyond the route-level role gate) - no bug there. Donation creation, idempotency handling, and the timeline/blockchain-verification endpoints were already solid.
- Full backend syntax sweep and full-app frontend bundle both clean after this checkpoint's changes.

## Checkpoint 18 — Phase 3: Merchant flow (QR generate → scan → confirm → settlement) traced end to end

## Checkpoint 19 — Phase 4: Government/Admin oversight and blockchain anchoring; the two most emphasized areas of this audit turned out to have the two most severe bugs found all session

This checkpoint covered fraud alerting and blockchain anchoring - the platform's core trust story. Both were broken in ways that produced no visible errors, which is why they'd survived this long.

**Fraud alerts were never actually being saved, at all.** `fraud.worker.js` called `FraudAlert.create({entityType: "Wallet", reason, riskScore, signals, detectedAt})` - but the real schema requires `alertId` (unique) and `alertType` (enum) which were never supplied, uses `entityType: "WALLET"` (uppercase, schema-enforced) not `"Wallet"`, and has no top-level `reason`/`riskScore`/`signals`/`detectedAt` fields at all (they live under `aiDetection.*`/`metadata.*`). Every single call threw a Mongoose ValidationError. Because the whole worker body runs in one try/catch, the error was silently swallowed and logged to console only - meaning the auto-freeze-wallet-on-high-risk branch never reached its own `wallet.save()` call either (the throw happened first), so **automatic wallet freezing on high fraud risk silently never took effect**, on top of zero fraud alerts ever existing. Fixed with a proper schema-matching builder used at both call sites (auto-freeze and escalate-decision).

**A second, completely disconnected fraud-tracking system was fully built and permanently empty.** There are two separate models for the same concept: `FraudAlert` (fed by the worker above, read by the public/government/NGO dashboards and the trust-scoring engine) and `FraudCase` (a richer model with investigation status, assignment, notes, and resolution - backing a fully-built admin page, `FraudManagement.jsx`, with working resolve/assign/notes UI and matching backend routes in `fraud.controller.js`). Nothing anywhere in the codebase ever created a `FraudCase` record - confirmed via exhaustive grep for `FraudCase.create`/`new FraudCase` before concluding this, not assumed. The entire admin fraud-investigation workflow - UI, routes, and controller all fully working - was structurally guaranteed to always show zero cases, no matter how much real fraud activity occurred. Fixed by having the fraud worker create a matching `FraudCase` alongside every `FraudAlert`, so the already-built investigation UI finally receives real data.

**Donation blockchain anchoring - "the main part" per this project's own stated value proposition - never actually anchored a single donation.** `donation.worker.js` queues a blockchain job as `{type: "DONATION", entityId, data}`. The consuming worker checked for a `proofId` field first (which donation jobs never carry) and, finding none, fell through to a generic "legacy batch" branch that ran a real batch anchor transaction but wrote the result to a fabricated audit-log entry - `entityType: "Proof"` (hardcoded, wrong) and `entityId: job.id` (the internal queue job ID, not the donation) - and never touched the `Donation` document at all. `Donation.blockchainHash` / `blockchainAnchored` / `blockchainAnchoredAt` - the exact fields the donor-facing "verify this donation on the blockchain" screen reads (`donation.blockchain.service.js`) - were never set by anything, ever. Every donation would show as permanently unverified regardless of what actually happened on-chain. Added a real `type === "DONATION"` branch: records the event, anchors it, and writes the result back onto the specific donation.

**A second, adjacent gap found while fixing the above:** even for the proof-anchoring path that *was* already wired correctly to its own entity, the resulting audit log entries never populated `AuditLog.merkleRoot` / `AuditLog.blockchainAnchor.txHash` - the exact dedicated schema fields (separate from the generic `payload` blob) that `public.service.js getBlockchainStatus()` queries to show the public "is blockchain anchoring operational" badge. `createAuditLog()` accepted a `payload` object but had no code path writing to those dedicated fields at all, so the public transparency status could never report anything but "PENDING - no anchors yet," permanently, regardless of real on-chain activity. Fixed `createAuditLog()` to accept and persist `merkleRoot`/`blockchainAnchor` properly, and updated all three blockchain-anchor audit log call sites (donation, proof, and legacy-batch) to populate them.

Verified (not touched): admin campaign approve/reject vs. government campaign pause/close is a clean, non-duplicated separation of concerns (onboarding gate vs. ongoing oversight), not an architectural overlap like the fraud models above.

Full backend syntax sweep and full-app frontend bundle both clean after this checkpoint's changes.

## Checkpoint 23 — Phase 6: infrastructure sweep turned up the most severe issue found all session

Went looking at layers not yet checked - file storage, appeal authorization, password reset - rather than re-treading UI ground with diminishing returns.

- **CRITICAL SECURITY: the password reset endpoint handed back the raw reset token in its own API response.** `requestPasswordReset()` returned `{ message, resetToken }` unconditionally - the actual comment on that line was `// Remove this in production`. In practice this meant: anyone who knew or could guess *any* user's email address - including an admin's - could call `POST /auth/forgot-password`, read the reset token straight out of the JSON response, and immediately call `POST /auth/reset-password` to take over that account. No access to the victim's inbox required at all, because no real email-sending integration exists anywhere in this codebase to begin with (confirmed - no nodemailer/SES/SendGrid/Twilio in package.json or anywhere in source). This is a full, unauthenticated account-takeover path for any account on the platform, and was very likely the single highest-severity finding of the entire audit. Fixed by gating the token to non-production environments only (so local testing still works without needing a real email provider configured) and logging it server-side instead of putting it on the wire.
- **Uploaded proof-of-distribution files were unreachable.** `fileStorage.service.js` writes files to disk and hands back a URL like `/uploads/proofs/<file>` in local-storage mode (the default), but nothing in `app.js` ever served that path - there was no `express.static` mount for it at all. Every proof photo the frontend tried to display would 404. Compounding it: even after adding the static route, the URL was still relative, and the frontend (`services/api.js`) calls the backend via an absolute cross-origin URL with no dev proxy configured - a relative `/uploads/...` `<img src>` resolves against the *frontend's* own origin, not the backend's, so it would 404 regardless. Fixed both: added the static route, and changed `storeFileLocally` to return an absolute, backend-rooted URL (S3 mode was unaffected either way, it already returns real signed URLs).
- **Access-control gap: any beneficiary could submit an appeal on behalf of any other beneficiary.** `submitAppeal`'s controller passed the target record's id straight from the URL param into the service with no check that it belonged to the requesting user - any authenticated beneficiary could flip *someone else's* rejected application back into manual review just by knowing their record id. Added the missing ownership check.
- Full backend syntax sweep and full-app frontend bundle both clean after this checkpoint's changes.
